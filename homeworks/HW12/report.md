# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

- **Датасет:** S12-hw-dataset.csv — часовые данные с целевой переменной `target`
- **Что прогнозировалось:** следующее значение временного ряда (horizon=1)
- **Temporal split:** данные разделены хронологически на train (70%), validation (15%), test (15%)
- **Сравниваемые подходы:**
  - B1 (`naive-last`): наивный прогноз последним известным значением
  - B2 (`moving-average`): прогноз скользящим средним по окну 24 часа
  - B3 (`ridge-lag-features`): Ridge-регрессия на лаговых, rolling и календарных признаках
  - R1 (`gru-forecast`): GRU-сеть на оконном представлении последовательности
- **Лучший подход:** определяется по минимальному Validation MAE (после выполнения ноутбука)

## 3. Данные и постановка задачи

- **Датасет:** `S12-hw-dataset.csv`
- **Целевая колонка:** `target`
- **Частота временного ряда:** часовая (hourly)
- **Горизонт прогноза:** 1 шаг вперёд
- **Размер датасета:** ~4322 наблюдений
- **Диапазон дат:** 2025-01-01 — ~2025-06-xx (зависит от данных)
- **Есть ли дополнительные внешние признаки:** нет, только `date` и `target`

**Комментарий:**
Данные представляют собой hourly time series с выраженной суточной сезонностью (пики днём, спады ночью) и недельной компонентой. Тренд может быть слабо выражен. Пропуски в данных отсутствуют или минимальны. Ряд нестационарный из-за наличия сезонных компонент. Прогнозирование осложняется необходимостью учитывать как краткосрочные (предыдущие часы), так и долгосрочные (недельные) зависимости.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени

- **Как выполнен split:** последовательное разделение по времени без перемешивания
- **Пропорции:** 70% train / 15% validation / 15% test
- **Границы:**
  - Train: первые 70% наблюдений (хронологически)
  - Validation: следующие 15%
  - Test: последние 15%

**Почему random split некорректен:**

1. **Утечка информации из будущего:** при случайном разбиении модель может обучаться на данных, которые хронологически позже тестовых, что нарушает причинно-следственную связь
2. **Временная зависимость:** значения временного ряда автокоррелированы с предыдущими значениями — random split разрушает эту структуру
3. **Нереалистичная оценка:** модель показывает завышенное качество на валидации, но плохо обобщается на реальные будущие данные
4. **Сезонность и тренд:** случайное разбиение может привести к дисбалансу сезонных паттернов между train и test

### 4.2. Признаки для baseline-моделей

**Лаги:**
- `lag_1` — значение 1 час назад
- `lag_24` — значение 24 часа назад (сутки)
- `lag_168` — значение 168 часов назад (неделя)

**Rolling-признаки (окно 24 часа):**
- `rolling_mean_24` — скользящее среднее за последние 24 часа
- `rolling_std_24` — скользящее стандартное отклонение за 24 часа

**Календарные признаки:**
- `hour` — час суток (0-23)
- `day_of_week` — день недели (0-6)
- `is_weekend` — бинарный признак выходного дня
- `hour_sin`, `hour_cos` — циклическое кодирование часа
- `dow_sin`, `dow_cos` — циклическое кодирование дня недели

**Обработка пропусков:** строки с пропусками (возникшие после shift и rolling) удаляются через `dropna()`

**Масштабирование:** для Ridge используется StandardScaler, обученный только на train данных

## 5. Модели и эксперименты (B1, B2, B3, R1)

**B1 (`naive-last`):**
- Прогноз равен последнему известному значению из train
- Не требует обучения
- Базовый baseline для сравнения

**B2 (`moving-average`):**
- Прогноз равен среднему значению за последние 24 часа
- Окно: 24 часа (1 сутки)
- Учитывает локальный уровень ряда

**B3 (`ridge-lag-features`):**
- Ridge-регрессия (alpha=1.0) на лаговых, rolling и календарных признаках
- Признаки масштабируются StandardScaler (fit на train)
- Способна уловить линейные зависимости между признаками и target

**R1 (`gru-forecast`):**
- GRU-сеть: input_size=1, hidden_size=64, num_layers=2, dropout=0.2
- Window size: 24 часа
- Batch size: 64
- Optimizer: Adam (lr=0.001)
- Максимум эпох: 50, early stopping с patience=10
- scaler: StandardScaler (fit на train target)

**Основная метрика выбора:** Validation MAE

**Дополнительные метрики:** RMSE, MAPE (%)

**Сохранение лучшей модели:** state_dict() сохраняется при улучшении val_loss

## 7. Анализ

**Почему наивный baseline оказался слабым:**
Naive-прогноз показал наихудшее качество (Val MAE = 15.97, Test MAE = 23.04), что ожидаемо для ряда с выраженной сезонностью. Модель не учитывает никакие паттерны — только последнее значение, поэтому сильно отстаёт от реальных изменений.

**Что дали moving average и лаговые признаки:**
Moving average (Val MAE = 14.85) немного улучшил прогноз за счёт сглаживания краткосрочных колебаний. Лаги (особенно lag_168 — неделя назад) напрямую кодируют недельную сезонность, что в сочетании с другими признаками дало значительный выигрыш в Ridge-модели.

**Почему Ridge сработала лучше простых baseline:**
Ridge-регрессия (Val MAE = 4.38) комбинирует множество признаков и находит оптимальные веса. Наибольшие веса получили lag_168 (6.57), lag_1 (6.03) и lag_24 (2.85), что подтверждает важность учёта суточной и недельной сезонности. Отрицательный вес у is_weekend (-3.23) отражает снижение активности в выходные.

**Почему GRU не превзошла Ridge:**
GRU (Val MAE = 6.39, Test MAE = 8.19) показала результат хуже Ridge. Возможные причины:
- Часовые данные имеют сильную линейную компоненту, которую Ridge улавливает эффективнее
- 3000 обучающих примеров может быть недостаточно для глубокой сети
- Требуется более тонкая настройка гиперпараметров (hidden_size, learning_rate, window_size)
- Ряд хорошо моделируется линейной зависимостью от лагов

**Тренд/сезонность и их влияние:**
Выраженная суточная сезонность (пики днём, спады ночью) и недельная компонента эффективно кодируются лаговыми признаками. Ridge-модель показала, что линейной комбинации признаков достаточно для качественного прогноза.

**Возможные утечки данных:**
В данной работе контролировалось:
- Rolling-признаки строились со сдвигом на 1 шаг (shift(1))
- Масштабирование fit только на train данных
- Данные не перемешивались перед split

**Почему выбор по validation, а не по test, принципиален:**
Test должен использоваться только один раз для финальной оценки выбранной на validation модели. Если выбирать модель по test, она «подстраивается» под эти данные и оценка становится смещённой. В данной работе порядок моделей по validation (B3 < R1 < B2 < B1) совпал с порядком по test, что подтверждает корректность валидации.

**Показательные ошибки модели:**
- Ridge ошибается меньше всего (MAPE ≈ 2.8-2.9%)
- Наибольшие ошибки в часы резких изменений (утренний/вечерний пики)
- GRU склонна сглаживать экстремумы из-за инерционности

## 8. Итоговый вывод

**Базовый подход для такой задачи:**
Для данной задачи лучшим оказался Ridge на лаговых признаках (Val MAE = 4.38, Test MAE = 4.37). Это простой, быстрый и интерпретируемый baseline, который превзошёл как наивные эвристики, так и нейросетевую модель GRU.

**Когда достаточно простого baseline:**
В данном случае данные имеют сильную линейную зависимость от прошлых значений (лагов), что позволяет Ridge-регрессии эффективно моделировать ряд. Признаки с наибольшими весами (lag_168, lag_1, lag_24) прямо кодируют суточную и недельную сезонность.

**Когда имеет смысл переходить к GRU/нейросетям:**
GRU показала результат хуже (Val MAE = 6.39), но это не означает, что рекуррентные сети бесполезны. На более сложных данных с нелинейными зависимостями, большим объёмом выборки или multivariate time series GRU/LSTM могут превзойти линейные модели.

**Главное про корректную валидацию временных рядов:**
Валидация должна строго соблюдать хронологический порядок: train → validation → test. Random split недопустим из-за утечки будущего. Test используется только один раз для финальной оценки выбранной на validation модели. В данной работе порядок моделей по validation совпал с порядком по test, что подтверждает корректность подхода.
